Architecture

How the pieces fit: the page model, the chrome module, the blog engine, the theme registry, and the styling system.

The page model

Each content page is intentionally thin. It carries a static <head> (charset, title, stylesheet links, fonts), one attribute on the body, and its own <main>. Nothing else.

<body data-page="projects">
    <main> … unique page content … </main>
    <script src="chrome.js"></script>
    <script src="script.js"></script>
</body>

The data-page value is the seam between a page and the shared chrome. chrome.js reads it to highlight the matching nav link. The post page uses data-page="blog" so "Blog" stays active while reading an article.

chrome.js — the shared chrome

Everything every page used to repeat — the nav, the footer, the theme switcher, and their behaviour — lives here once. On load it injects the markup into the body and wires up the behaviour.

Its interface is three data tables plus one attribute:

  • NAV — the nav links. Add an entry → the link appears on every page.
  • SOCIAL — the footer links.
  • THEMES — the colour palettes (see below).
  • <body data-page> — which nav link is active.

Behaviour it owns: theme cycling + persistence (localStorage), and nav-shrink-on-scroll. Because the nav exists in exactly one place, the classic "edited four pages, forgot the fifth" drift bug cannot happen.

The blog engine

The blog has one source of truth — posts.js — and two consumers. Adding a post never touches HTML.

posts.js  (const POSTS = [ { slug, title, date, excerpt, tags?, readMins? } ])
   │
   ├─ blog.html   → renderBlogIndex()
   │       sorts POSTS newest-first, builds a card per post into #post-list
   │
   └─ post.html?slug=x → renderPost()
           1. look up x in POSTS   (only known slugs are fetchable)
           2. set title + meta from the manifest entry
           3. fetch posts/x.md
           4. marked.parse() → #post-content

Both renderers live in script.js and share postMetaHtml() so the tag/date/read-time markup is defined once. Titles and excerpts are HTML-escaped before injection; dates are parsed by hand to avoid timezone shifts.

Why a single reader? There is one post.html, not one HTML file per post. The post pages vary only by content, and the content is the Markdown file — so the page is a parameterised reader, not N copies.

The theme registry

A theme is just data: two inks and their soft tints.

{ id:'tangerine', ink1:'#f0530e', ink1soft:'#f8a072',
  ink2:'#1f4fd6', ink2soft:'#8aa6f2' }

applyTheme() writes these onto :root as the CSS custom properties --ink-1, --ink-1-soft, --ink-2, --ink-2-soft. There are no per-theme blocks in style.css to keep in sync — the :root values are only a no-JS fallback (the default tangerine palette). The switcher cycles the THEMES array and saves the chosen id.

script.js — page-content behaviour

What's left after chrome moved out: smooth-scroll for in-page anchors, the blog renderers, the Projects tab switcher, and the Contact form handler (client-side only — it logs and shows a thank-you; there is no backend). Each concern self-gates on the elements it needs, so the one file is safe to load on every page.

style.css — the design system

Tokens live on :root: paper, ink-black/soft, the two inks + tints, hard shadow values, and a shared transition. The risograph look is built from a few repeated devices:

  • Grain — an SVG turbulence overlay fixed over the page (body::after, multiply blend).
  • Halftone — two offset radial-gradient dot grids on the body background.
  • Hard offset shadows — Npx Npx 0 (no blur). Hover "presses" a card into its shadow.
  • Misregistration — headings get an offset ink text-shadow, mimicking mis-aligned ink layers.
  • Flat ink blocks — 3px black borders, chips, and buttons share one card recipe.

Why these shapes

The recurring move is depth: a small interface in front of a lot of behaviour, so a change lands in one place. Add a nav link in NAV; a post in posts.js; a palette in THEMES. The duplication that used to spread edits across files (and let copies drift) is gone.
